# 실무에 바로 적용할 수 있는 체크리스트

## 사용 기준

> - 프로젝트 시작 전에는 문제 정의와 데이터 사용 가능성을 먼저 확인합니다.
> - 모델링 중에는 누출, 데이터 분리, 평가지표, 오류 분석을 반복 점검합니다.
> - 배포 전에는 재현성, 보안, 모니터링, 운영 책임자를 확인합니다.
> - 아래 항목은 실무 프로젝트 리뷰 회의에서 그대로 사용할 수 있도록 세분화했습니다.

## A. 문제 정의와 비즈니스 목표

| 체크 | 점검 항목 | 실무 완료 기준 |
|---|---|---|
| ☐ | 업무 문제 명확화 | 예측/분류/군집화 결과가 해결하려는 실제 업무 문제를 한 문장으로 작성했다. |
| ☐ | 사용자 정의 | 모델 결과를 사용할 현업 부서, 담당자, 의사결정권자를 정의했다. |
| ☐ | 의사결정 연결 | 모델 점수 또는 예측값이 어떤 액션으로 이어지는지 정의했다. |
| ☐ | 타깃 정의 | 타깃 변수의 정의, 단위, 생성 기준, 관측 시점을 명확히 했다. |
| ☐ | 예측 시점 정의 | 모델이 언제 예측하는지와 그 시점에 사용 가능한 변수를 구분했다. |
| ☐ | 성과 기준 합의 | 정확도, 비용 절감, 매출 증가, 리스크 감소 등 성공 기준을 현업과 합의했다. |
| ☐ | 대안 비교 | 모델 없이 규칙 기반으로 해결할 수 있는지, 모델이 필요한 이유를 확인했다. |
| ☐ | 범위 제한 | 이번 프로젝트에서 하지 않을 것과 다음 단계로 미룰 것을 명확히 했다. |

## B. 데이터 확보와 거버넌스

| 체크 | 점검 항목 | 실무 완료 기준 |
|---|---|---|
| ☐ | 데이터 출처 기록 | 각 테이블/파일의 생성 시스템, 담당 부서, 업데이트 주기를 기록했다. |
| ☐ | 데이터 권한 확인 | 개인정보/민감정보/계약 데이터 사용 권한을 확인했다. |
| ☐ | 개인정보 최소화 | 모델링에 불필요한 이름, 전화번호, 이메일, 주민번호 등 직접 식별자를 제거했다. |
| ☐ | 데이터 기간 확인 | 학습 데이터 기간이 충분하며 특정 이벤트 기간에 치우치지 않았는지 확인했다. |
| ☐ | 데이터 단위 확인 | 고객 단위, 주문 단위, 일자 단위 등 분석 단위를 명확히 했다. |
| ☐ | 중복 데이터 확인 | 중복 키, 중복 주문, 중복 고객이 모델 학습을 왜곡하지 않는지 확인했다. |
| ☐ | 라벨 품질 확인 | 타깃 라벨이 정확하고 일관되게 생성되는지 샘플 검증했다. |
| ☐ | 데이터 사전 작성 | 컬럼명, 의미, 단위, 결측 의미, 허용 범위를 데이터 사전으로 정리했다. |
| ☐ | 보관 정책 확인 | 원본 데이터, 전처리 데이터, 모델 결과의 보관 기간과 접근 권한을 정했다. |

## C. 데이터 누출 방지

| 체크 | 점검 항목 | 실무 완료 기준 |
|---|---|---|
| ☐ | 예측 시점 이후 변수 제거 | 예측 시점 이후에만 알 수 있는 사후 결과 변수를 제거했다. |
| ☐ | 타깃 파생 변수 확인 | 타깃 계산식에 직접 들어가는 변수를 입력에서 제외하거나 별도 검토했다. |
| ☐ | 집계 기간 점검 | 최근 30일/90일 집계 변수가 예측 기준일 이후 데이터를 포함하지 않는지 확인했다. |
| ☐ | ID 누출 점검 | 고객ID/상품ID/매장ID가 라벨을 암기하게 만들지 않는지 확인했다. |
| ☐ | 데이터 분리 전 전처리 금지 | 스케일링, 인코딩, 결측 대체를 train/test 분리 전에 전체 데이터로 fit하지 않았다. |
| ☐ | SMOTE 적용 위치 | SMOTE나 오버샘플링은 학습 데이터에만 적용했다. |
| ☐ | 검증셋 누출 확인 | 튜닝 과정에서 테스트셋을 반복적으로 보며 과적합하지 않았다. |
| ☐ | 운영 가능 변수 확인 | 실제 운영 환경에서 즉시 조회 가능한 변수만 최종 모델에 사용했다. |

## D. EDA와 데이터 품질

|---|---|---|
| ☐ | 결측치 비율 확인 | 컬럼별 결측 비율과 결측 발생 원인을 확인했다. |
| ☐ | 이상치 확인 | 숫자형 변수의 극단값을 시각화하고 실제값인지 오류인지 판단했다. |
| ☐ | 범주값 정리 | 범주형 변수의 오탈자, 대소문자, 공백, 희귀 범주를 정리했다. |
| ☐ | 분포 확인 | 타깃과 주요 입력 변수의 분포를 히스토그램/박스플롯으로 확인했다. |
| ☐ | 상관관계 확인 | 강한 상관 변수, 중복 변수, 다중공선성 위험 변수를 확인했다. |
| ☐ | 시간 패턴 확인 | 월별/요일별/시즌별 변동이 있는지 확인했다. |
| ☐ | 그룹별 차이 확인 | 지역, 채널, 상품군, 고객군별 타깃 차이를 확인했다. |
| ☐ | 데이터 불균형 확인 | 분류 문제에서 양성 클래스 비율과 희귀 이벤트 여부를 확인했다. |
| ☐ | 군집화 변수 분포 확인 | 군집화 변수는 스케일과 분포가 지나치게 왜곡되지 않았는지 확인했다. |

## E. 전처리와 피처 엔지니어링

| 체크 | 점검 항목 | 실무 완료 기준 |
|---|---|---|
| ☐ | 전처리 파이프라인화 | 결측 대체, 스케일링, 인코딩을 Pipeline/ColumnTransformer로 묶었다. |
| ☐ | 숫자형 처리 | 숫자형 결측 대체 방식과 스케일링 필요성을 기록했다. |
| ☐ | 범주형 처리 | 범주형 인코딩 방식과 미지 범주 처리(handle_unknown)를 설정했다. |
| ☐ | 날짜 파생변수 | 월, 요일, 주말, 월말, 시즌, 경과일 등 의미 있는 날짜 변수를 만들었다. |
| ☐ | 비즈니스 파생변수 | 비율, 차이, 변화량, 누적값 등 업무적으로 해석 가능한 변수를 만들었다. |
| ☐ | 희귀 범주 처리 | 샘플 수가 적은 범주를 Other로 묶거나 별도 처리했다. |
| ☐ | 스케일링 기준 | 선형/거리/딥러닝 모델에는 스케일링을 적용하고, 트리 모델의 필요성은 구분했다. |
| ☐ | 타깃 변환 검토 | 회귀 타깃이 심하게 왜곡되면 log1p 등 변환을 검토했다. |
| ☐ | 재현 가능성 확보 | 전처리 과정이 노트북 재실행 시 동일하게 수행되도록 작성했다. |

## F. 데이터 분리와 검증 설계

| 체크 | 점검 항목 | 실무 완료 기준 |
|---|---|---|
| ☐ | 랜덤 분리 적절성 검토 | 일반 랜덤 split이 실제 운영 상황을 반영하는지 검토했다. |
| ☐ | 시간 기준 분리 | 미래 예측 문제에서는 과거 학습/미래 평가 방식으로 검증했다. |
| ☐ | 그룹 기준 분리 | 같은 고객/매장/상품이 train/test에 동시에 들어가면 안 되는 경우 GroupSplit을 사용했다. |
| ☐ | Stratify 적용 | 분류 문제에서는 클래스 비율이 유지되도록 stratify를 적용했다. |
| ☐ | 교차검증 설계 | 데이터 크기와 업무 특성에 맞게 KFold, StratifiedKFold, TimeSeriesSplit을 선택했다. |
| ☐ | 검증셋 역할 분리 | 튜닝용 validation과 최종 테스트셋을 구분했다. |
| ☐ | 데이터 기간 문서화 | 학습/검증/테스트 기간과 샘플 수를 기록했다. |

## G. 모델링 전략

| 체크 | 점검 항목 | 실무 완료 기준 |
|---|---|---|
| ☐ | 기준 모델 확보 | 가장 단순한 baseline 모델을 먼저 만들었다. |

| ☐ | 하이퍼파라미터 범위 | 튜닝할 파라미터와 범위를 사전에 정했다. |

| ☐ | 과적합 방지 | 정규화, Dropout, EarlyStopping, 교차검증 등을 적용했다. |
| ☐ | 모델 저장 계획 | 최종 모델, 전처리 객체, 버전 정보를 함께 저장할 계획을 세웠다. |

## H. 평가지표와 비용 해석

| 체크 | 점검 항목 | 실무 완료 기준 |
|---|---|---|
| ☐ | 회귀 지표 선택 | MAE, RMSE, R² 중 업무에 적합한 주 지표를 정했다. |
| ☐ | 분류 지표 선택 | Accuracy, Precision, Recall, F1, ROC-AUC, PR-AUC의 역할을 구분했다. |

| ☐ | 비용 기반 평가 | FP/FN 또는 과대/과소예측 비용을 현업 기준으로 정의했다. |
| ☐ | 임계값 정책 | 분류 모델의 threshold를 업무 리소스와 비용에 맞게 선택했다. |
| ☐ | 세그먼트별 성능 | 지역/고객군/상품군별 성능 차이를 확인했다. |
| ☐ | 통계적 안정성 | 단일 split 결과가 아니라 교차검증 또는 반복 실험으로 안정성을 확인했다. |

## I. 오류 분석과 모델 해석

| 체크 | 점검 항목 | 실무 완료 기준 |
|---|---|---|
| ☐ | 오류 샘플 추출 | 회귀는 절대오차 큰 샘플, 분류는 FP/FN 샘플을 추출했다. |
| ☐ | 오류 공통점 분석 | 오류가 특정 기간, 지역, 상품군, 고객군에 집중되는지 확인했다. |
| ☐ | 잔차 분석 | 회귀 모델 잔차가 특정 예측값 구간에서 커지는지 확인했다. |
| ☐ | 변수 중요도 확인 | Permutation Importance 또는 모델 기반 중요도를 확인했다. |
| ☐ | 선형 계수 해석 | 선형 모델의 계수 방향과 크기를 업무적으로 설명했다. |
| ☐ | 딥러닝 해석 한계 | DNN은 성능이 좋아도 해석 가능성이 낮을 수 있음을 명시했다. |
| ☐ | 현업 검증 | 모델이 중요하다고 판단한 변수가 현업 상식과 일치하는지 검토했다. |
| ☐ | 개선 아이디어 도출 | 오류 분석을 기반으로 추가 데이터 또는 파생변수 아이디어를 정리했다. |

| ☐ | 모델 사용 한계 고지 | 모델 결과는 의사결정 보조이며 자동 결정의 한계를 명시한다. |
| ☐ | 감사 가능성 | 데이터, 코드, 모델, 결과가 추적 가능하도록 버전 관리한다. |

## L. 산출물과 커뮤니케이션

| 체크 | 점검 항목 | 실무 완료 기준 |
|---|---|---|
| ☐ | 문제 정의 1장 | 목표, 타깃, 예측 시점, 기대 효과를 한 장으로 정리했다. |
| ☐ | 데이터 요약 | 데이터 기간, 건수, 주요 변수, 결측/이상치 처리 내용을 정리했다. |
| ☐ | 모델 비교표 | 후보 모델과 주요 성능 지표를 표로 제시했다. |
| ☐ | 최종 모델 선정 이유 | 성능, 안정성, 해석 가능성, 운영 가능성을 근거로 설명했다. |
| ☐ | 오류 분석 | 대표 오류 사례와 개선 방향을 포함했다. |
| ☐ | 액션 전략 | 예측 결과를 기반으로 어떤 업무 조치를 할지 제안했다. |
| ☐ | 한계와 다음 단계 | 현재 데이터와 모델의 한계, 추가 실험 계획을 작성했다. |
| ☐ | 코드 재현성 | 다른 사람이 노트북을 처음부터 실행해도 같은 결과가 나오도록 정리했다. |

## 최종 프로젝트 제출 전 20문항 빠른 점검

| 체크 | 빠른 질문 | 완료 기준 |
|---|---|---|
| ☐ | 문제 정의가 한 문장으로 명확한가? | 문제, 타깃, 사용자가 명확히 드러난다. |
| ☐ | 예측 시점이 정의되어 있는가? | 언제 예측하고 그때 어떤 변수를 알 수 있는지 설명한다. |
| ☐ | 누출 변수를 제거했는가? | 사후 결과/타깃 파생/미래 정보를 제거했다. |
| ☐ | train/test 분리 방식이 적절한가? | 랜덤/시간/그룹 분리 중 업무에 맞는 방식을 선택했다. |
| ☐ | 전처리가 Pipeline으로 구성되어 있는가? | 재현 가능하고 누출 없는 전처리 구조다. |
| ☐ | 기준 모델이 있는가? | 복잡한 모델 전 baseline을 만들었다. |
| ☐ | 평가지표 선택 이유가 있는가? | 업무 비용과 지표를 연결했다. |
| ☐ | 성능표가 비교 가능하게 정리되었는가? | 모델별 동일 지표로 비교했다. |
| ☐ | 오류 분석을 했는가? | 오차 큰 샘플 또는 FP/FN 샘플을 확인했다. |
| ☐ | 변수 중요도 또는 해석이 있는가? | 결과를 현업 언어로 설명했다. |
| ☐ | 임계값을 검토했는가? | 분류 모델은 0.5 고정이 아니라 정책 기준을 검토했다. |
| ☐ | 과적합 여부를 확인했는가? | 교차검증/학습곡선/validation 성능을 확인했다. |
| ☐ | 세그먼트별 성능 차이를 봤는가? | 특정 그룹에서 성능이 나쁜지 확인했다. |
| ☐ | 운영 액션이 있는가? | 예측 후 누가 무엇을 할지 정의했다. |
| ☐ | 모델 한계를 작성했는가? | 데이터/모델/업무 적용 한계를 솔직히 적었다. |
| ☐ | 추가 데이터 제안이 있는가? | 성능 개선을 위한 데이터 아이디어가 있다. |
| ☐ | 코드가 처음부터 실행되는가? | 런타임 재시작 후 전체 실행이 가능하다. |
| ☐ | 파일 경로가 상대경로인가? | 다른 PC에서도 데이터 로드가 가능하다. |
| ☐ | 발표 흐름이 논리적인가? | 문제-데이터-모델-결과-전략-한계 순서다. |
| ☐ | 질문에 답할 준비가 되었는가? | 왜 이 모델/지표/변수를 선택했는지 설명할 수 있다. |

## 마지막 한 줄 기준

> - 좋은 실습 결과는 “코드가 돌아갔다”가 아니라 “왜 이 결과가 나왔고, 실무에서 어떻게 쓸지 설명할 수 있다”입니다.
> - 프로젝트 발표에서는 성능 숫자보다 문제 정의, 누출 방지, 오류 분석, 액션 전략이 더 강한 설득력을 만듭니다.
